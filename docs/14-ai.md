# 14. AI

Engi talks to chat models through one provider-neutral port. This page covers the model layer
that the AI nodes build on: the `port.LLM` contract, the provider adapters, credential types,
the shared tool contract, token metrics and the `engi.ai.chat` node. The agent loop, memory,
RAG and MCP are later phases of the same area (see [Roadmap](12-roadmap.md)). The generic mechanism that wires them together is in
[14.8 Sub-ports](#148-sub-ports).

## 14.1 Architecture

```
engi.ai.chat node ──► port.LLMFactory ──► metrics ─► timeout ─► adapter ──HTTP──► provider
 (internal/node)       (internal/app, llm_providers.go)       (llmkit)    anthropic | openai | ollama
```

| Piece | Path | Role |
|---|---|---|
| `port.LLM` and its request/response types | `internal/port/llm.go` | The chat contract: `Chat` and `Stream` |
| Tool contract | `internal/port/aitool.go` | `Tool`, `ToolResult`, `Toolset`, plus the provider interfaces for sub-nodes |
| Adapters | `internal/adapter/llm/{anthropic,openai,ollama}` | One per API, call the HTTP APIs directly (no vendor SDKs) |
| Shared helpers | `internal/llmkit` | HTTP error mapping, SSE and NDJSON readers, timeout and metrics decorators. Outside `internal/adapter`, so adapters never import each other |
| Factory | `internal/app/llm_providers.go` | Builds a `port.LLM` from a provider id and a decrypted credential. It lives in the composition root because it picks concrete adapters (see docs/02, 2.1.1) |
| Credential types | `internal/credtype/{anthropic,openai,azureopenai,ollama}` | Field definitions (secrets marked) |
| Node | `internal/node/aichat` | `engi.ai.chat` |

Nodes never import adapters. The composition root (`internal/app`) builds the factory and gives it to
the node with the `WithLLMFactory` registry option; without it the node fails with
`nodesdk.ErrUnavailable`. Requests go through the shared outbound HTTP client (proxy, TLS and
tracing from [configuration](11-deployment.md)). The factory builds a client per call and caches
nothing, so editing a credential takes effect on the next run.

## 14.2 The `port.LLM` contract

```go
type LLM interface {
    Chat(ctx context.Context, req LLMRequest) (LLMResponse, error)
    Stream(ctx context.Context, req LLMRequest, emit func(StreamEvent) error) (LLMResponse, error)
}
```

**Request** (`LLMRequest`): `Model`, `System`, `Messages`, `Tools`, `ToolChoice`, `Temperature`,
`TopP`, `MaxTokens`, `Stop`, `Format`. Optional numbers are pointers (nil means provider default).

- A message has a role (`system`, `user`, `assistant`, `tool`). An assistant message may carry
  `ToolCalls` (id, name, JSON arguments). A tool message answers one call through `ToolCallID`, and
  sets `IsError` when the tool failed.
- A tool definition is a name, a description and a JSON Schema for the parameters.
- Tool choice is `auto`, `none`, `required` or a specific tool (`tool` plus `Name`).
- Response format is `text`, `json` (any JSON object) or `jsonSchema` (name plus schema).

**Response** (`LLMResponse`): `Content`, `ToolCalls`, `StopReason`, `Usage` (input and output
tokens) and `Model`. The stop reason is normalized to `end`, `maxTokens`, `toolUse`,
`stopSequence` or `other`.

**Streaming.** `Stream` calls `emit` with each text delta and returns the aggregated response, tool
calls included, so a caller can stream text and still run the agent loop on the result. An error
from `emit` aborts the request. Anthropic uses SSE, OpenAI uses SSE, Ollama uses NDJSON.

**Errors.** Failures are `*port.LLMError` (use `errors.As`): provider id, HTTP status, the
provider's message (never the request or the key), `Retryable` and the provider's `RetryAfter`.
429, 408, 5xx and transport failures are retryable; 4xx are not. A cancelled context returns the
context error. Config problems (unknown provider, missing key) are `*port.LLMConfigError`.
Retrying is the caller's choice: the node relies on the workflow's own retry settings.

### Provider differences

| Topic | Anthropic | OpenAI / Azure OpenAI | Ollama |
|---|---|---|---|
| Endpoint | `POST {base}/v1/messages` | `POST {base}/chat/completions` (Azure: `{endpoint}/openai/deployments/{model}/chat/completions?api-version=`) | `POST {base}/api/chat` |
| Auth | `x-api-key` plus `anthropic-version` | `Authorization: Bearer` (Azure: `api-key`) | optional bearer or custom header |
| Token cap | required; `nodes.ai.defaultMaxTokens` fills it | `max_completion_tokens` | `num_predict` |
| `json` format | system instruction (the API has no JSON mode) | `response_format: json_object` (adds a "respond with JSON" hint if the prompt never says JSON, which the API requires) | `format: "json"` |
| `jsonSchema` format | **forced tool** (below) | `response_format: json_schema`, strict | `format: <schema>` |
| Tool choice | native | native | emulated: `none` drops tools, a specific tool keeps only that tool, `required` is best effort |
| Tool-call ids | from the API | from the API | generated by the client (Ollama has none) |
| Tool error flag | `is_error` | text prefixed with `Error:` | text prefixed with `Error:` |

**Anthropic `jsonSchema`.** Anthropic's Messages API has no portable structured-output switch across
models, so Engi emulates it: it adds one tool whose input schema is your schema and forces the model
to call it (`tool_choice` of that tool). The tool's arguments are returned as the reply text, the
call is hidden from `ToolCalls`, and the stop reason is reported as `end`. When the same request
also offers real tools, forcing is impossible, so the schema is appended to the system prompt
instead (best effort, the model is not constrained). When streaming, the argument fragments are
emitted as text deltas.

## 14.3 The shared tool contract

Defined once in `internal/port/aitool.go` so the agent, the tool providers and MCP do not depend on
each other.

```go
type Tool interface {
    Definition() ToolDefinition
    Call(ctx context.Context, args json.RawMessage) (ToolResult, error)
}
type ToolResult struct { Content string; IsError bool }
```

A tool that ran but failed in a way the model can react to returns `IsError: true` with a nil error
(the agent feeds it back as a tool message). A non-nil error means the tool could not run at all.
`Toolset` is an ordered, name-unique collection: `NewToolset` rejects empty and duplicate names
(`ErrDuplicateTool`), and it offers `Lookup`, `Definitions`, `Names` and `Call` (`ErrUnknownTool` for
a missing name). Two interfaces describe what a parent node will ask of its sub-nodes:
`ToolProvider` (`Tools(ctx) ([]Tool, error)`) and `ModelProvider` (`Model(ctx) (LLM, LLMRequest, error)`).
The model node implements `ModelProvider`, the tool sub-nodes implement `ToolProvider` (see 14.12 and 14.13).

(see [Deployment](11-deployment.md)); Azure always needs a deployment name.

## 14.5 The AI Chat node

`engi.ai.chat` (group `ai`) makes one model call per input item. Reference tables:
[Node Reference, AI](nodes/12-ai.md).

- **Provider** picks the API and therefore which credential slot is read; bind the credential of the
  matching type (the editor lists all four slots, only the selected provider's is used).
- **Model**, **System prompt**, **Message**, **Temperature** and **Max tokens** may be expressions and
  are resolved per item. Empty temperature and max tokens use the provider default.
- **Options**: `topP` and comma-separated `stopSequences`.
- **Response format**: `text`, `json`, or `jsonSchema` (with a schema name and a JSON Schema
  object or string).

**Output** per item (linked to its input item): `text`, `model`, `stopReason`,
`usage {inputTokens, outputTokens, totalTokens}` and, for the JSON formats, `json` with the parsed
reply. A reply wrapped in a Markdown code fence is accepted. An invalid reply fails the item, with a
hint to raise `maxTokens` when the stop reason was `maxTokens`.

**Errors** name the item and wrap the provider error (`calling anthropic: anthropic HTTP 429: ...`),
so `Retryable` stays visible to `errors.As`. Use the node's error handling (continue, error output,
retry) like any other node; there is no separate switch in the node.

**Example**

```json
{
  "provider": "ollama",
  "model": "llama3.2:3b",
  "systemPrompt": "You classify support tickets.",
  "message": "={{ $json.subject }}",
  "responseFormat": "jsonSchema",
  "schemaName": "ticket",
  "schema": { "type": "object", "properties": { "priority": { "type": "string" } }, "required": ["priority"] }
}
```

**Chat node.** `engi.ai.chat` is a standalone node with its own credential and structured-output modes; the
sub-port design (`ai.model`, `ai.tool`, `ai.memory`, [Data Model 3.3](03-data-model.md)) is used by the AI Agent (14.12). The chat node always runs one model call per item and returns usage and the normalized stop
reason on every item.

## 14.6 Configuration

All keys are in the `nodes.ai.*` block of the [config table](11-deployment.md): provider base URLs and

included). Histogram buckets for model-call duration are `observability.metrics.buckets.llm`.

## 14.8 Sub-ports

AI nodes compose through **sub-ports**: a parent (the agent, a RAG node) pulls values from the nodes
connected to its `ai.*` inputs; those sub-nodes never run as steps. The mechanism is generic and lives in
`pkg/nodesdk` (contract) and `internal/service/engine` (see [page 4](04-engine.md), Sub-ports); it knows
nothing about models or tools.

| Kind | Value type the parent type-asserts | Typical sub-node |
|---|---|---|
| `ai.model` | `port.ModelProvider` | model node |
| `ai.tool` | `port.ToolProvider` | workflow, HTTP, code, vector search, MCP tools |
| `ai.memory` | `port.ChatMemory` | window memory |
| `ai.embedding` | `port.Embedder` | embeddings ([14.10](#1410-rag-embeddings-text-splitter-and-pgvector)) |
| `ai.textSplitter` | `port.TextSplitter` | text splitter |
| `ai.vectorStore` | reserved (the pgvector node is a main node) | |

Adding another kind is one constant (any `ai.` name is valid); no engine change.

Rules:

- A sub-node has an `ai.*` output and no main ports, and implements `nodesdk.Supplier`. It may have its
  own sub-port inputs (a vector-search tool takes an `ai.vectorStore`).
- A parent declares inputs with `Kind: ai.*`, `Required` and `MaxConnections` (0 = unlimited). A required
  input without an enabled sub-node fails the parent before it runs; too many connections is rejected on
  save. Connections go sub-node output to parent input, same kind, one sub-node may feed several parents.
- `in.SubPort(ctx, kind, itemIndex)` supplies afresh on every call, in connection order, and skips
  disabled sub-nodes. Parameters and expressions of the sub-node resolve against the parent's item
  `itemIndex`, so an agent calls it per item. Cache what is expensive inside the parent for one item.
- Sub-node failures (including panics) fail the parent with `sub-node "Name" (type) failed: ...`.
- **Run data:** sub-nodes get no `NodeRun` and no observer events. What the editor shows about model and
  tool use comes from the parent's own output (the agent's `steps`). `$("Sub-node")` therefore has no data.

A tool sub-node, as a tool author writes it:

```go
func (n *Node) Describe() nodesdk.Descriptor {
	return nodesdk.Descriptor{Type: "engi.ai.tool.example", Version: 1, Group: nodesdk.GroupAI,
		Outputs: []nodesdk.PortSpec{{Name: "tool", Kind: nodesdk.PortAITool}}, Properties: props}
}
func (n *Node) Execute(context.Context, nodesdk.Input) (nodesdk.Output, error) { return nodesdk.Output{}, nodesdk.ErrUnavailable }
func (n *Node) Supply(ctx context.Context, in nodesdk.Input) (any, error) {
	name, err := nodesdk.ParamString(ctx, in, "name", 0) // item 0 here means the parent's current item
	if err != nil { return nil, err }
	return toolProvider{tools: []port.Tool{newExampleTool(name, in.HTTP())}}, nil // implements port.ToolProvider
}
```

The parent does `got, err := in.SubPort(ctx, nodesdk.PortAITool, i)` and, for each `got[k].Value`,
`v.(port.ToolProvider)`.

## 14.9 Testing

- Unit tests use `httptest` servers that play each provider (chat, tool calls, streaming,
  response formats, error mapping including 429 with `Retry-After`), a fake `port.LLM` for the node
  and the decorators, and a fake factory for the node.
- The adapters and the node have no network or Docker dependency in the default run.
- An optional live check of the Ollama adapter runs only when `ENGI_TEST_OLLAMA_URL` (for example
  `http://localhost:11434`) and `ENGI_TEST_OLLAMA_MODEL` (for example `llama3.2:3b`) are both set:
  `go test ./internal/adapter/llm/ollama -run TestLive -v`. Anthropic and OpenAI are never called
  from tests.

## Chat trigger

The `engi.trigger.chat` node turns a workflow into a chat backend: an HTTP endpoint for messages, a hosted
chat page, and a stable `sessionId` that the AI Agent's memory uses to keep a conversation together. It is
a webhook trigger underneath (same activation, same `webhook` role, same Respond to Webhook node), served
under its own base path, `chat.basePath` (default `/chat`), outside API authentication and CSRF.

### Routes

| Route | Purpose |
|---|---|
| `POST /chat/<path>` | Send one message; the answer is the workflow's reply |
| `OPTIONS /chat/<path>` | CORS preflight |
| `GET /chat/<path>/widget` | The hosted chat page |
| `GET /chat/<path>/widget.js`, `widget.css`, `loader.js` | Static files of the page and the embed loader |

A chat path may not end in `widget`, `widget.js`, `widget.css` or `loader.js`, and may not have `:param`
segments. Empty `path` means `<workflow id>/<node name as a slug>`. Chat paths are a separate namespace from webhook
paths: the route is registered under the pseudo method `CHAT`, which no real request carries, so
`/hook/<path>` never reaches a chat trigger. Two active chat triggers cannot share a path (activation fails
with a conflict, exactly like webhooks). The routes exist only while the workflow is active.

### Message contract

Request body, JSON, at most `chat.maxBodyBytes` (default 64 KiB, else 413):

```json
{ "sessionId": "optional", "message": "Where is my order?", "metadata": { "page": "/orders" } }
```

- `message` is required and must be a non-blank string. `chatInput` is accepted as an alias (it is the
  name the trigger item uses, so callers that already speak it need no change). If both are sent, `message` wins.
- `sessionId` is optional: at most `chat.maxSessionIdLength` (128) characters of `A-Z a-z 0-9 . _ : -`.
  When absent the server generates a random 128-bit id. The session id is returned in the JSON answer and in the
  `X-Chat-Session-Id` header (also when a Respond to Webhook node writes the body), and callers send it back
  to continue the conversation. It is a conversation key, not a secret: anyone who knows a session id can
  continue that session, so do not use guessable ids.
- `metadata` is an optional JSON object passed through untouched.

The trigger emits **one item** per message: `{ "sessionId": "...", "chatInput": "...", "metadata": {...} }`
(`metadata` only when sent). The [AI Agent](14-ai.md) reads `chatInput`; its memory node should use
`={{ $json.sessionId }}` as the session key.

### Response modes

| Mode | Behaviour |
|---|---|
| `lastNode` (default) | Holds the call until the execution ends. The reply is the `replyField` (default `output`, falling back to `text`) of the **first item** of the last node that ran. A string is used as is, any other JSON value is sent as JSON text. Answer: `200 {"sessionId", "output", "executionId"}` |
| `responseNode` | Holds the call until a [Respond to Webhook](nodes/02-flow.md#respond-to-webhook) node runs and sends exactly what it produces (status, headers, body); the workflow continues afterwards |

Errors: `500` when the run failed, `502` when the last node has neither field, `504` when no reply arrives
within `chat.responseTimeout` (default 50 s, below `server.writeTimeout`; the execution carries on), `202`
with `{sessionId, executionId, status}` when the run is waiting (a Wait node). There is no
"immediately" mode: a chat message without a reply has no use.

### Authentication

`none`, `basic` (`engi.http.basic` credential) or `header` (`engi.http.header`), checked before the body is
read and before any execution exists, with the webhook's constant-time comparison and a bare `401` that does
not say which part was wrong. Basic auth adds `WWW-Authenticate: Basic realm="chat"`.

### CORS (allowed origins)

The `allowedOrigins` option is a comma-separated list of origins, or `*`. A browser call whose `Origin` is
the serving origin is always allowed. A call with another `Origin` is answered `403` unless it is listed;
a listed origin gets `Access-Control-Allow-Origin: <origin>`, `Vary: Origin` and, on `OPTIONS`, `204` with
allowed methods `POST, OPTIONS`, the requested headers and `Access-Control-Max-Age` (`chat.preflightMaxAge`,
default 10 min). Calls without an `Origin` header (servers, curl) are not CORS requests and pass. CORS is not
authentication: it only controls which web pages may talk to the endpoint. The list also sets the widget's
`frame-ancestors`, so only those sites can embed it.

### The hosted widget

`GET /chat/<path>/widget` serves an own-design, framework-free chat page: plain HTML rendered with
`html/template` (title, welcome message and placeholder come from the node and are escaped), one CSS file and
one JavaScript file. There is no inline script or style, no CDN and no font download, so the page runs under
this policy:

```
default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none';
frame-ancestors 'self' | <allowedOrigins>
```

plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store` (static
files use `no-cache` with an ETag). Behaviour: the session id is kept in `sessionStorage` per chat path (every
access is wrapped in try/catch, so the page still works when storage is blocked); replies are inserted with
`textContent` only, so model output can never inject markup; Enter sends and Shift+Enter adds a line; the log
is `role="log"` with `aria-live="polite"`, the input has a visible-to-assistive-tech label, errors use
`role="alert"`, focus rings are visible, layout is fluid down to phone width (`100dvh`), and colours follow
`prefers-color-scheme`. The widget is only served when authentication is `none` (browsers cannot hold the
secret safely): other chat triggers answer `403` and should be called directly.

**Embedding.** Either use an iframe, or load the floating-button loader, which injects the button and an
iframe of the widget (styles are set through the DOM, so a strict host page CSP only needs to allow the chat
host in `script-src` and `frame-src`):

```html
<script src="https://engi.example.com/chat/support/loader.js" async data-label="Chat" data-side="right"></script>
<!-- or -->
<iframe src="https://engi.example.com/chat/support/widget" title="Chat" style="width:380px;height:600px;border:0"></iframe>
```

Add the embedding site to the node's `allowedOrigins`, otherwise both the iframe (`frame-ancestors`) and the
calls (CORS) are refused.

### Editor: "Open chat"

The node panel of a chat trigger shows **Open chat**, a link to the widget in a new tab. Chat routes exist
only while the saved workflow is active and the editor's test-listen mechanism is webhook-specific (armed
one-shot test URLs, manual-mode runs), so the button is disabled with the reason when the workflow is
inactive, when the node is not saved yet, or when authentication is not `none`. It builds the URL from the
saved path and the server's `chat.basePath`, which the editor reads from `GET /api/v1/me`
(`editor.chatBasePath`), so a changed base path needs no editor rebuild.

### Streaming: not built, design for a follow-up

Token streaming needs a way for a node that is still running to hand partial output to the caller. The
engine has no such channel, and the Agent and the node SDK are another job's contract, so replies are
delivered whole for now. Proposed design, additive and backward compatible:

1. SDK: `nodesdk.Input.Stream() nodesdk.Streamer` (nil when the caller did not ask for streaming), with
   `Streamer.Chunk(ctx, text string)`. Nodes that cannot stream ignore it; the Agent calls it from its
   `port.LLM` stream loop for the text of the final answer only (not tool-call turns).
2. Engine: `Chunk` publishes `port.EventNodeChunk{ExecutionID, Node, Text}` on the bus (the bus already
   carries `EventNodeFinished` for Respond to Webhook, so cluster mode works the same way).
3. HTTP: when the request has `Accept: text/event-stream` and the mode is `lastNode`, the chat handler subscribes
   before starting (as `responseNode` does), writes `event: chunk` frames with `data: {"text": ...}`, and ends with
   `event: done` carrying `{sessionId, output}` (the same body as the non-streaming answer) or `event: error`.
   `chat.responseTimeout` becomes an idle timeout between frames; `server.writeTimeout` must be extended per
   request with `http.ResponseController.SetWriteDeadline`.
4. Widget: read the stream with `fetch` and `ReadableStream`, appending to the bubble with `textContent`.

| Key | Env | Default |
|---|---|---|
| `chat.basePath` | `ENGI_CHAT_BASE_PATH` | `/chat` |
| `chat.maxBodyBytes` | `ENGI_CHAT_MAX_BODY_BYTES` | `65536` |
| `chat.maxSessionIdLength` | `ENGI_CHAT_MAX_SESSION_ID_LENGTH` | `128` |
| `chat.responseTimeout` | `ENGI_CHAT_RESPONSE_TIMEOUT` | `50s` |
| `chat.preflightMaxAge` | `ENGI_CHAT_PREFLIGHT_MAX_AGE` | `10m` |

(The YAML section is the top-level `chat` key, env `ENGI_CHAT_*`; see [Deployment](11-deployment.md#115-configuration).)

### Chat trigger behaviour

Each chat trigger has a public chat URL for hosted and embedded use, a session id the agent memory keys on, `chatInput` as the item field, last-node and responding-node modes, allowed origins and optional authentication. The request is a small JSON contract (`message`, optional `chatInput` alias). There is no "load previous session" action: history lives in the memory node, not the trigger. The widget is Engi's own code and CSS and works under a strict CSP. Authentication uses Engi's credential types, and chat paths are their own namespace.

## 14.10 RAG: embeddings, text splitter and pgvector

Retrieval-augmented generation is four nodes and two ports. Chunks of your documents are embedded and
stored in a PostgreSQL table with the [pgvector](https://github.com/pgvector/pgvector) extension; at question
time the nearest chunks are fetched and handed to a model (the agent through a tool, or any workflow through the
Vector Store node's search).

| Node | Type | Role |
|---|---|---|
| Text Splitter | `engi.ai.textSplitter` | sub-node, output `ai.textSplitter`, supplies a `port.TextSplitter` |
| Embeddings | `engi.ai.embeddings` | sub-node, output `ai.embedding`, supplies a `port.Embedder` |
| Vector Store | `engi.ai.vectorStore` | main node: `insert`, `search`, `delete` on a pgvector table |
| Vector Search Tool | `engi.ai.tool.vectorSearch` | sub-node, output `ai.tool`, one tool `{query}` for an agent |

### Embedder port and adapters

```go
type Embedder interface {
    Embed(ctx context.Context, texts []string) (EmbedResult, error) // one vector per text, in order
}
type EmbedderFactory interface {
    New(provider string, cred nodesdk.Credential, set EmbedderSettings, httpc nodesdk.HTTPClient) (Embedder, error)
}
```

An `Embedder` is bound to provider, credential and model (`EmbedderSettings{Model, Dimensions}`) when built, so
callers pass only texts. `EmbedResult` carries `Vectors`, `Model`, `Dimensions` and summed `Usage.InputTokens`.
The factory is `internal/adapter/embedding`, injected into the registry with `app.WithEmbedderFactory`.

| Provider | Endpoint | Credential type |
|---|---|---|
| `openai` | `POST {baseUrl}/embeddings` (Bearer) | `engi.openai` |
| `azureopenai` | `POST {endpoint}/openai/deployments/{deployment}/embeddings?api-version=` (`api-key`) | `engi.azureOpenAI` |
| `ollama` | `POST {baseUrl}/api/embed` | `engi.ollama` |
| `anthropic` | none: Anthropic has no embeddings API, the factory returns a config error | |

The adapter splits input into batches of `nodes.ai.rag.embeddingBatchSize` texts and sends them one after another
(no fan-out), each bounded by `nodes.ai.rag.embeddingRequestTimeout`. Vectors from one call must all have the same
length. Errors are `*port.LLMError` (429 and 5xx are `Retryable`, `Retry-After` is parsed), the same type the chat
adapters return. `dimensions` is sent only when set (OpenAI `text-embedding-3*`, recent Ollama).

**Metrics.** Embeddings get their own metric family instead of an `operation` label on the LLM metrics, because their
shape differs (no output tokens, one input-token count) and changing `LLMCall` would break every `port.Metrics`
implementation. `port.EmbeddingMetrics` is a separate interface that the Prometheus adapter and `NopMetrics`
implement; the factory records through it when the injected `Metrics` also implements it.

| Metric | Labels |
|---|---|
| `engi_embedding_requests_total` | `provider`, `model`, `outcome` (`ok`, `rate_limited`, `error`) |
| `engi_embedding_request_duration_seconds` | `provider`, `model` (buckets: `observability.metrics.buckets.llm`) |
| `engi_embedding_tokens_total` | `provider`, `model` |

One observation is recorded per `Embed` call (all batches together).

### Text splitter

`engi.ai.textSplitter` supplies a recursive character splitter (`aitextsplitter.Recursive`). It tries the first
separator that occurs in the text (default order: paragraph, line, space, character), cuts there, cuts pieces that
are still too long with the next separator, and packs neighbouring small pieces into chunks of at most `chunkSize`
characters with `chunkOverlap` characters carried into the next chunk. Parameters: `chunkSize` (1000),
`chunkOverlap` (200, must be below the size), `separators` (JSON array; `""` cuts between characters) and
`keepSeparator` (true: the separator stays at the start of the piece that followed it). Lengths count Unicode
characters, so multi-byte text and emoji are never cut inside a character. Chunks are trimmed and empty ones dropped.
**Splitter.** Engi has one recursive splitter, whose separator list covers the character case. There is no token-based length and no Markdown or code mode.

### Vector Store node and pgvector layout

The node uses the user's `engi.postgres` credential through the same shared pools as the Postgres node
(`port.DBPool` injected as `sqlnode.Pools`), so connection reuse, limits and credential-edit handling are identical.
The SQL lives in `internal/node/pgvector` (statement builders plus `Insert`, `Search`, `Delete` over `database/sql`),
which nodes may import because it is node-layer code, not an adapter.

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE IF NOT EXISTS "schema"."table" (
  id        text PRIMARY KEY,                       -- your document id (+ #n per chunk) or a random UUID
  content   text NOT NULL,                          -- the chunk text
  metadata  jsonb NOT NULL DEFAULT '{}'::jsonb,     -- your metadata + chunkIndex, chunkCount
  embedding vector(N) NOT NULL                      -- N = the embedding model's size, fixed at creation
);
CREATE INDEX IF NOT EXISTS "table_embedding_idx" ON "schema"."table" USING hnsw (embedding vector_cosine_ops);
```

- **Dimensions.** `vector(N)` is fixed when the table is created, from the first vector inserted. Inserting a
  different size fails in PostgreSQL and the node adds a hint; use one model (and `dimensions`) per table. Searching
  with a different model than the one used to insert fails the same way.
- **Creation is opt-in** (`createIfMissing`, off by default): without it the node only runs `INSERT`, so it works
  with a role that cannot create extensions or tables. `createIndex` adds an HNSW index (pgvector indexes at most
  2000 dimensions).
- **Distance** (`cosine` default, `l2`, `innerProduct`) selects the operator (`<=>`, `<->`, `<#>`) and the index
  operator class. It is a query-time choice, not stored. Results carry the raw `distance` and a `score` that grows
  with similarity: cosine similarity `1 - d`, `1 / (1 + d)` for L2, the inner product for `innerProduct`.
  An index only speeds up searches that use the metric it was built for.
- **Insert** reads `text`, `metadata` and optional `id` per input item, splits (if a splitter is connected), embeds
  all chunks of all items in one `Embed` call, and upserts in one transaction (`ON CONFLICT (id) DO UPDATE`, in
  batches of `nodes.ai.rag.insertBatchSize` rows). With an `id`, inserting again replaces the document: in the same
  transaction, before the new chunks are written, its earlier chunks are deleted (`id` for one chunk, `id#0`,
  `id#1`... for several). A document that shrank leaves no stale chunks. Ids that only look like chunks of the
  document (`id2`, `id#x`) are kept, and an item without an `id` only upserts. The delete matches by id prefix, so
  PostgreSQL scans the table for each re-ingested document (there is no index on the document key). Output: one
  item per input item with `ids` and `chunks`.
- **Search** embeds the `query` of every input item in one call and returns one item per match: `id`, `text`,
  `metadata`, `score`, `distance`, paired to the input item. `topK` is bounded by `nodes.ai.rag.maxTopK`. The
  optional `filter` object keeps rows whose metadata contains it (`metadata @> filter`, so equality on keys and
  nested objects).
- **Delete** by `ids` and/or `filter` (both: a row must match both). It refuses to run with neither, and accepts at
  most `nodes.ai.rag.maxDeleteIds` ids. Output: `{deleted}` per input item.
- The **Embedding** input is required (max 1, also for delete, because the engine checks sub-ports before the node
  runs); the **Text splitter** input is optional (max 1).
- **Safety.** Every value is a bound parameter (vectors and JSON as text cast on the server:
  `$1::text::vector`, `$2::text::jsonb`). Table and schema names must match `[A-Za-z_][A-Za-z0-9_]*` (at most 48
  characters, which leaves room for the index name) and are quoted anyway.

### Vector Search tool

`engi.ai.tool.vectorSearch` takes a Postgres credential, schema/table, distance, `topK`, an optional fixed metadata
`filter`, a tool `name` (default `search_documents`, `[a-zA-Z0-9_-]{1,64}`) and a `description` the model reads, plus
a required `ai.embedding` sub-input. It supplies one tool with the argument `{"query": "..."}`. The result is a JSON
array of `{id, text, metadata, score}`. Empty or malformed arguments return an error result the model can react to; a
failing embedding call or database returns an error. Use one tool node (with a distinct name and description) per
knowledge base.

```
Embeddings ──ai.embedding──▶ Vector Search Tool ──ai.tool──▶ AI Agent
```

**Design.** Engi ships pgvector only (it reuses a database most users already run) and splits ingest from agent use: the Vector Store node is a normal workflow step, the tool is a sub-node. There is no document loader node; feed text from the HTTP, file or database nodes into `text`. Search returns the score and distance and supports an explicit distance setting. The filter is always jsonb containment.

### Testing

Embedders are tested against `httptest` fakes (batching, ordering, Azure URL and header, Ollama, 429 and error
mapping, mixed dimensions, metrics). The splitter has table-driven and invariant tests including multi-byte text.
The SQL layer is tested as pure statement builders plus a recording fake `database/sql` driver
(`internal/node/pgvector/pgvectortest`); the nodes are tested with a fake embedder, the real splitter sub-node and that
driver. There is no local pgvector server, so the live check is written but opt-in: with build tag `integration` and
Docker: with build tag `integration`, `go test -tags integration ./internal/node/pgvector -run Live -v` starts a
`pgvector/pgvector:pg17` container (testcontainers) and creates and drops its own tables. Set
`ENGI_TEST_PGVECTOR_DSN` to a PostgreSQL DSN with pgvector available to use that server instead. The live tests
cover the metrics, filters, the upsert, and document replacement, including a rollback when the re-insert fails.

## 14.11 MCP client tool and MCP server trigger

The [Model Context Protocol](https://modelcontextprotocol.io) (MCP) lets an AI client discover and call tools on
a server. Engi implements both sides with the standard library only (no MCP SDK): the protocol code is in
`internal/mcp`, a leaf package that nodes, services and adapters can all import because it depends on nothing
else in Engi.

| Piece | Path | Role |
|---|---|---|
| JSON-RPC types, client (both transports), server dispatcher | `internal/mcp` | `Connect`, `ListTools`, `CallTool`, `Server.Handle` |
| Credential type `engi.mcp` | `internal/credtype/mcp` | none / bearer / custom header for the client |
| MCP Client tool | `internal/node/aitoolmcp` | `engi.ai.tool.mcp`, sub-node with an `ai.tool` output |
| MCP Server trigger node | `internal/node/mcpservertrigger` | `engi.trigger.mcpServer`, describes and validates |
| Use cases | `internal/service/mcpserver` | resolve an endpoint, list tools, run a tool's workflow |
| HTTP adapter | `internal/adapter/http/mcpserver` | `/mcp/<path>`: auth, size limit, origin check |

**Protocol revisions.** `2025-11-25`, `2025-06-18`, `2025-03-26` and `2024-11-05`. The client offers the newest
and accepts any of them in the server's answer; the server answers `initialize` with the client's version when it
knows it and with its newest otherwise. After the handshake both sides use the `MCP-Protocol-Version` header.

### MCP Client tool (`engi.ai.tool.mcp`)

A sub-node (see [14.8](#148-sub-ports)) that gives the connected agent the tools of a remote MCP server.

- **Parameters.** `endpoint` (URL), `transport` (`streamableHttp` default, or `sse`), `authentication` (`none`, or
  `credential` to send the bound `engi.mcp` credential), and the tool selection: all, `selected` (named tools) or
  `allExcept`. A selected name the server does not offer fails the node with a clear message.
- **Credential `engi.mcp`.** Authentication `none`, `bearer` (`Authorization: Bearer <token>`) or `header` (any
  header name plus a secret value). Names and values with line breaks are refused.
- **Transports.** Streamable HTTP: every message is a POST; the reply is `application/json` or an SSE stream that
  ends with the response (progress notifications on the way are ignored); `Mcp-Session-Id` is kept and sent back,
  a 404 on a request that carries it is `ErrSessionExpired`, and closing sends `DELETE` (a 405 is fine). The legacy
  HTTP+SSE transport opens `GET <endpoint>`, waits for the `endpoint` event, POSTs requests there and reads the
  responses from the stream; an endpoint on another origin is refused so credentials cannot be redirected.
  **Fallback:** with `streamableHttp`, a client error (400, 404, 405, 406, 415...) on the first `initialize` POST
  retries over `sse`, as the spec's compatibility rules describe; 401, 403, 408 and 429 do not fall back, so a
  wrong token is reported as such instead of being hidden by a second attempt.
- **Listing.** `tools/list` follows `nextCursor` up to `nodes.mcp.maxListPages` pages and `nodes.mcp.maxTools`
  tools; a server beyond either fails the node rather than silently losing tools.
- **Calling.** The result's text parts are joined with newlines (`image`/`audio` parts become a short placeholder,
  embedded text resources their text, and `structuredContent` is used when there are no parts). `isError: true`
  becomes `ToolResult.IsError`. A JSON-RPC error (bad arguments, unknown tool) is also fed back to the model as an
  error result; connection problems are returned as errors. Output over `nodes.mcp.maxResultBytes` is cut on a
  character boundary and marked.
- **Names.** The model sees `[a-zA-Z0-9_-]{1,64}`, the limit OpenAI and Anthropic both accept. Each tool name is `<prefix>__<server tool name>`: the prefix is
  the sub-node's name with other characters turned into `_` and cut to 24 characters (an empty name becomes `tool`).
  So `search` on a sub-node named `MCP Alpha` is offered as `MCP_Alpha__search`, and the call goes to the server as
  `search`. The prefix is always applied, so a tool's name does not change when another server is connected. Long
  names are cut to 64 characters and clashes within one server get `_2`, `_3`. Two sub-nodes whose prefixes match
  (for example `Mail Server` and `Mail_Server`) still clash; the agent then fails the item and names both sub-nodes.
  The 24-character prefix limit is `maxToolPrefixLength` in `internal/node/aitoolmcp`.
- **Connections are short-lived.** The tool contract has no close hook, so `Tools` and each `Call` open a session,
  do their work and close it before returning (one stream goroutine at most, joined on close). That costs a
  handshake per call but leaks nothing and copes with servers that expire sessions.
- Requests go through the shared outbound HTTP client, so proxy, TLS and its response cap apply. Per-request
  time limit: `nodes.mcp.requestTimeout`.

### MCP Server trigger (`engi.trigger.mcpServer`)

While the workflow is active, `POST /mcp/<path>` is a Streamable HTTP MCP server whose tools are workflows. See also
[8.12](08-triggers.md#812-mcp-server-trigger-as-built).

- **Tools.** The node lists tools as `{name, description, workflowId, inputSchema}`. The workflow must start with an
  Execute Workflow Trigger node (the first enabled one is used). `inputSchema` is a JSON object schema (or its
  text); empty accepts any object.
- **Methods.** `initialize`, `notifications/initialized`, `ping`, `tools/list` (no pagination: one page) and
  `tools/call`. Batches are accepted. Anything else is "method not found".
- **A call** runs the workflow synchronously (`RunSync`, mode `webhook`) with the arguments as its one input item
  and answers with the last node's output as JSON text: one item is an object, several are an array, none is `[]`.
  Binary data is not returned. The wait is bounded by `mcpServer.callTimeout`.
- **Errors.** A workflow that fails, times out, waits, does not exist or does not start with an Execute Workflow
  Trigger is a result with `isError: true` (internal details are logged, not sent). Unknown tool and non-object
  arguments are `-32602`; more than `mcpServer.maxConcurrentCalls` calls at once is `-32000` "server busy"; an
  unexpected failure is `-32603`.
- **Transport.** Replies are always `application/json`. The server is **stateless**: it issues no `Mcp-Session-Id`,
  any request may come first, and a client can use any number of replicas behind a load balancer. `GET` (the
  optional server-to-client stream) and `DELETE` get 405 with `Allow: POST`, which the spec permits; Engi therefore
  sends no server-initiated notifications (no `listChanged`, no progress). Notifications and responses get 202.
- **Auth and limits.** None, bearer or header token (constant-time compare, before the body is read; 401 with
  `WWW-Authenticate: Bearer` for bearer). A request that carries an `Origin` header must name an origin in
  `mcpServer.allowedOrigins` (empty refuses every browser request), which is the spec's guard against DNS
  rebinding; non-browser clients send no `Origin`. The body is capped by `mcpServer.maxBodyBytes` (413). A request
  with an unsupported `MCP-Protocol-Version` header gets 400.
- **Not built.** A manual "listen" test mode (the webhook test URL has no MCP counterpart; test with a client
  against the active workflow), sessions with `Mcp-Session-Id` and SSE streams, resources and prompts, and OAuth
  for the client are follow-ups.

**Design.** The MCP Server trigger exposes whole workflows (each a sub-workflow with an Execute Workflow Trigger) and is stateless, so it works across replicas, but it speaks Streamable HTTP only. The MCP client tool opens a session per list and per call (no leaks, no close hook needed) and authenticates with none, bearer or a custom header. The client falls back from Streamable HTTP to SSE on 4xx, automatically, and never on an auth failure.

**Testing.** `internal/mcp` tests run a fake MCP server (JSON replies, SSE replies and the legacy transport) for
pagination, session ids, expiry, fallback, limits, timeouts and cancellation; the server handler tests cover every
method, authentication kind, the body cap and the origin check; a round-trip test drives the client tool against the
real handler, and `internal/app` activates a real workflow with an MCP trigger and calls it with the client. All
traffic is on localhost.

## 14.12 AI Agent

`engi.ai.agent` runs a tool-using loop per input item. It has one main input and output plus three sub-port
inputs: **`ai.model`** (required, at most one), **`ai.memory`** (at most one) and **`ai.tool`** (any number).
Reference tables: [Node Reference, AI](nodes/12-ai.md).

**Inputs.** The default prompt is `={{ $json.chatInput }}`, which is what the [chat trigger](#chat-trigger) emits
together with `sessionId`; set the prompt explicitly for any other source. An empty prompt fails the item with a
hint instead of sending nothing. `systemPrompt` is appended to any system text the model node supplies.

**The loop** (one item):

1. Build the request from the model node's template (model, temperature, max tokens...), the system prompt, the
   memory history, the user prompt, the tool definitions and the response format.
2. Call the model. No tool calls in the reply ends the loop; that reply is the answer.
3. Otherwise run every requested tool, in parallel with at most `nodes.ai.agent.toolConcurrency` at once, and append
   the assistant message and one tool message per call (in call order). Go to 2.

Tool failures never fail the node. A tool that returns an error result, returns a Go error, panics or is not found
produces a tool message with `IsError` set, so the model can correct itself (an unknown name lists the available
tools). Results larger than `nodes.ai.agent.maxToolResultBytes` are cut on a character boundary with a note.
Duplicate tool names across the connected tool nodes fail the item before any call. The error names both sub-nodes
that offer the name (or the one sub-node that offers it twice), so the fix is to rename one tool or its sub-node. MCP
tools are prefixed with their sub-node name (14.11), so a clash there only happens when two sub-node names map to the
same prefix. Model errors (including `*port.LLMError`, so retryability stays visible) fail the item; use the node's
retry and error settings.

**Limits**, defaults from `nodes.ai.agent.*` and overridable per node (empty = default): `maxIterations` (model
calls), `maxTotalTokens` (input plus output of all calls, checked before each call), `timeoutSeconds` (the whole item,
tools included; tools see the cancelled context). When one is reached the item **fails** with a message naming the
limit, or, with `onLimit = return`, returns what exists with `stopReason` set.

**Output item** (linked to its input item):

```json
{ "output": "It is 4 degrees in Oslo.",
  "steps": [ { "tool": "weather", "callId": "c1", "iteration": 1, "input": {"city": "Oslo"},
               "output": {"temp": 4}, "isError": false, "durationMs": 12 } ],
  "iterations": 2, "stopReason": "end", "model": "claude-sonnet-5-5",
  "usage": { "inputTokens": 640, "outputTokens": 85, "totalTokens": 725 } }
```

`stopReason` is `end`, `maxIterations`, `tokenBudget` or `timeout`. A step's `input` is the parsed arguments and
`output` is parsed JSON when the tool returned JSON, else the text. With response format `json` or `jsonSchema` the
parsed final reply is also in `json` (the reply must be valid JSON or the item fails; for Anthropic with tools the
schema is best effort, see 14.2). The editor shows `steps` as a collapsible list in the node's data tab.

**Memory.** With a memory node connected, the agent loads the history before the call and, after a run that ended
normally (`stopReason = end`), saves the exchange: the question and the final answer, or with `saveToolMessages` the
tool calls and results too (bigger, more faithful). Nothing is saved on failure or when a limit stopped the run.

### Window Memory (`engi.ai.memory.window`) and the chat memory store

The node supplies a `port.ChatMemory` bound to one session: `History`, `Save`, `Clear`. Parameters: **session key**
(default `={{ $json.sessionId }}`, resolved against the agent's current item; an empty key fails clearly rather than
sharing one global conversation) and **window size** (empty = `nodes.ai.memory.defaultWindow`, capped by `maxWindow`).
Messages are stored per workflow: the store key is the workflow id plus the session key, so equal session ids in two
workflows never mix. The window is the last N messages, then trimmed to start at a user message so it never begins
inside a tool exchange (providers reject that).

`port.ChatMemoryStore` (`Load(session, limit)`, `Append`, `Clear`) is implemented by the SQLite and Postgres store
adapters on the `chat_messages` table (**migration 0006** on both drivers; Postgres also has 0005, the SQLite
migrator accepts the gap since it tracks versions, not a count) and passes one contract suite
(`porttest.RunChatMemorySuite`). Rows hold role, content, tool calls (JSON), tool call id and the error flag, ordered
by an auto id. The store enforces `nodes.ai.memory.maxMessages` per session (oldest dropped on append) and
`nodes.ai.memory.retention` (older messages deleted on every append, an indexed delete). Without a persistent runtime
(`engi run` without `--persist`) the node fails with `ErrUnavailable`.

### AI Model (`engi.ai.model`)

A sub-node (output `ai.model`) with the provider, model, temperature, max tokens, top P and stop sequences of
`engi.ai.chat`, and the same four credential slots (bind the one matching the provider). `Supply` builds the client
through `port.LLMFactory` per call and returns a `port.ModelProvider` (client plus request template). An empty model
uses the provider default from config.

## 14.13 Tool sub-nodes

All tool nodes have an `ai.tool` output, a **tool name** (`[a-zA-Z0-9_-]{1,64}`, validated when supplied) and a
**description**, and where it makes sense an **arguments schema** (JSON Schema object; `required` entries must be
defined properties). Before a tool runs, the model's arguments are parsed as an object and checked for the required
keys; a failure is an error result for the model.

- **Workflow tool** (`engi.ai.tool.workflow`): runs another workflow through the existing sub-workflow runner. The
  arguments become the JSON of one input item of the child's Execute Workflow Trigger; the child's last-node output
  is the result (one item as an object, several as an array). A failed or timed-out child is an error result.
  Nesting counts against `engine.maxSubworkflowDepth` (checked when supplied, like Execute Workflow);
  `nodes.ai.tool.workflowTimeout` bounds a run.
- **HTTP tool** (`engi.ai.tool.http`): one request template. Method, URL, query, headers and body may contain
  `{name}` placeholders; each must be a property of the arguments schema (checked when supplied). Path values are
  path-escaped, query values query-escaped, header values must not contain line breaks. A JSON body keeps types:
  a string that is exactly `{name}` becomes the argument as given, other strings are interpolated. **The model
  cannot choose the host**: placeholders in the scheme or host are rejected, which stops a prompt-injected model from
  steering requests to arbitrary servers. Authentication is optional, with the HTTP Request node's predefined and
  generic credential types. The request goes through `in.HTTP()` (shared client, proxy and tracing); the body
  returned is cut at `nodes.ai.tool.httpMaxResponseBytes`; non-2xx is an error result with status and body;
  `nodes.ai.tool.httpTimeout` bounds a call.
- **Code tool** (`engi.ai.tool.code`): JavaScript in the Code node's goja sandbox (`code.NewSnippet`, same frozen
  built-ins and `nodes.code.*` time, recursion and size limits). The arguments are the object `args`; `$fn` and
  `console` are available, there is no item or workflow scope. A string result is returned as is, anything else as
  JSON. Syntax errors fail when supplied; runtime errors and timeouts are error results.

**Design.** Engi implements the tool-calling loop only, with window memory. Tool arguments are declared with an explicit schema, so the model's contract is visible and checked. A workflow tool passes the arguments as the child's input item. The window memory is keyed per workflow and stored in the database, not kept in process memory. Hitting a limit fails by default, with `onLimit` as the opt-in partial result, and token usage across the loop is returned on every item.

**Testing.** Agent tests use a scripted fake `port.LLM` and fake tools and memory: tool round trips, parallel
bounded calls, error feedback, every limit, structured output, memory round trip. Tool tests use fake runners and an
in-memory HTTP transport. The store contract suite runs on SQLite in unit tests and on Postgres with the
`integration` tag. `internal/app` validates a workflow wired with all sub-port kinds against the real descriptors. An
optional live run of the agent against Ollama (a code tool, `llama3.2:3b`) runs only when `ENGI_TEST_OLLAMA_URL` and
`ENGI_TEST_OLLAMA_MODEL` are set: `go test ./internal/app -run TestLiveOllamaAgent -v`.
